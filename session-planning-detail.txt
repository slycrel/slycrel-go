# Slycrel: Port to Go Terminal App

## Context

Slycrel is a text-based RPG "door game" written ~30 years ago by Jeremy Stone
and Dave Dolinar for the Hermes II BBS (Mac Classic). Originally Pascal, later
ported to C++ by Bill Dolinar. The goal is a faithful recreation in Go as a
terminal application, architected for future expansion (web frontend, BBS
integration, client/server).

The original source lives at orig/Legacy Code/Slycrel updated/ and contains
~70+ game states across 20+ source files implementing: character creation
(3 classes), a town hub with 18 locations, dual combat systems (ANSI grid +
text narrative), PvP arena with betting, inn ownership, tavern NPCs, economy,
leveling, and daily upkeep.

## Architecture

### Project Structure

  cmd/slycrel/main.go             // entry point
  internal/
    model/                        // Data structs (from SlyHeaders.h)
      character.go, monster.go, weapon.go, armor.go,
      inn.go, arena.go, town.go, combat.go, enums.go
    game/                         // Game engine
      engine.go                   // Session manager, multiplayer coordination
      session.go                  // Per-player state, owns state machine
      statemachine.go             // State registry, SetNextState/SetReturnState/Pop
      state.go                    // State interface
      states/                     // One file per location/flow
        main.go, town.go, wilderness.go, combat_text.go, combat_grid.go,
        tavern.go, inn.go, bank.go, healer.go, herbalist.go, armory.go,
        arena.go, common_guild.go, tower.go, blacksmith.go, jail.go,
        character_create.go, quit.go
    mechanics/                    // Pure game logic, no I/O
      chargen.go, leveling.go, damage.go, initiative.go, disposition.go,
      resurrection.go, upkeep.go, pathfinding.go, terrain.go,
      arena_calc.go, flirt.go, drinks.go
    io/                           // I/O abstraction (replaces Hermes BBS framework)
      terminal.go                 // IOProvider interface
      ansi.go                     // ANSI escape helpers
      terminal_impl.go            // Local terminal impl (x/term raw mode)
      prompt.go                   // LettersPrompt, NumbersPrompt, YesNo
    store/                        // Data persistence
      store.go                    // Store interface
      json_store.go               // JSON file implementation
  data/                           // Game data files (JSON)
    monsters/, weapons.json, armor.json, terrain/, ansi/, town_defaults.json
  orig/                           // Legacy source (read-only reference)

### Key Design Decisions

1. Raw ANSI output, no TUI framework — The original speaks ANSI natively. Raw
   output means the same stream works for terminal, telnet, or xterm.js
   WebSocket. No Bubble Tea or tcell.

2. Preserve the state machine — The original's SetNextState/SetReturnState/
   PopReturnState pattern maps cleanly to a Go interface + map + stack. Each
   ST_* function becomes a State struct. This makes 1:1 verification against
   the original straightforward.

3. IOProvider interface — Replaces all Hermes BBS I/O (G_Outln, G_ANSICode,
   G_LettersPrompt, etc.). Implementations: local terminal now, WebSocket/
   telnet later.

4. JSON data files — Replaces Mac Classic binary TItemFile<T> records.
   Human-readable, easy to edit and extend.

5. Multi-player ready from start — GameEngine manages sessions keyed by
   username. Shared Store with sync.RWMutex. Single-session for terminal, but
   the architecture supports concurrent sessions.

6. internal/ convention — All game code unexported. Only cmd/slycrel/ is the
   public entry point.

### Core Interfaces

IOProvider (replaces Hermes BBS callbacks):
  - Outln(text, newline, color), ANSICode(code), Cr(), ClearScreen()
  - LettersPrompt(prompt, allowed, maxChars, capitalize, autoAccept) string
  - NumbersPrompt(prompt, allowed, max, min) string
  - YesNoQuestion(prompt) bool
  - ShowANSIFile(name) error

State (game flow):
  - ID() StateID
  - Enter(ctx *Session) — does I/O and calls ctx.SM.SetNextState()

Store (persistence):
  - CRUD for characters, monsters, weapons, armor, inn, arena, town config, mail

## Implementation Phases

### Phase 1: Foundation
- go mod init, directory structure, all model structs
- IOProvider interface + local terminal impl (x/term raw mode, ANSI output)
- Store interface + JSON file impl (characters only)
- StateMachine (SetNextState/SetReturnState/Pop)
- Session, GameEngine, main.go wiring
- Deliverable: app launches, shows blank terminal, quits cleanly

### Phase 2: Character Creation + Town Hub
- RollChar (stat ranges per class from Sly_MainUnit.cp)
- Character creation flow (name, class, gender, color, reroll, view)
- Town menu with routing stubs for all locations
- Save/quit flow, Opening ANSI screen
- Deliverable: create character, view stats, enter town, save, quit

### Phase 3: Text Combat
- Damage formulas (from Sly_TextCombatUnit.cp)
- Initiative, disposition system (9 states)
- Wilderness exploration (daily limit: 15)
- Full text combat loop (Attack/Block/Parry/Dodge/Special/Run)
- Monster data files, random encounter selection
- Death/resurrection mechanics
- Deliverable: explore, fight monsters, gain XP/coins, die and resurrect

### Phase 4: Economy
- Bank (deposit/withdraw)
- Armory (buy/sell weapons/armor)
- Healer (HP restoration), Herbalist (Psyche restoration)
- Equipment data files
- Deliverable: full economic loop

### Phase 5: Leveling
- f(x) = LevelUpDifficulty * x^3 + f(x-1), base 50 XP
- Common Guild level advancement, stat increases per class
- Deliverable: characters level up

### Phase 6: Social (Tavern + Inn)
- Tavern: drinks, Lynx, Corenne flirt mechanics, hang around
- Inn: room rental, ownership, daily charges
- Deliverable: full tavern and inn

### Phase 7: Arena + PvP
- Gladiator challenges, betting, odds calculation
- Fight resolution, payoffs, mail/news system
- Daily upkeep (resolve fights, inn charges, resurrection)
- Deliverable: PvP system working

### Phase 8: Grid Combat
- Terrain types, movement costs, 12x48 map rendering
- Dijkstra pathfinding for monster AI
- Player movement (IJKL keys), ranged attacks
- Deliverable: full ANSI grid combat

### Phase 9: Remaining Locations + Polish
- Tower, Blacksmith, Jail, class-specific guild stubs
- High scores, all ANSI art menus
- Daily upkeep scheduler

### Phase 10: Multi-user + Future Frontends
- TCP/telnet server, WebSocket + xterm.js
- Concurrent session management
- User authentication with password hashing

## Verification
- After each phase: manually play through the implemented features in terminal
- Compare game flow against original source state-by-state
- Verify formulas by running same inputs through Go mechanics and comparing
  to C++ expected outputs
- Test multiplayer readiness: create multiple characters, verify shared state
